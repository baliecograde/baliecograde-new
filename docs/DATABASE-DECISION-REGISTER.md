## PostgreSQL compatibility: `NUMERIC Infinity`

Draft SQL memakai unconstrained `NUMERIC` untuk `location_accuracy_m` dan membatasi `< 'Infinity'::numeric`. Numeric Infinity didukung PostgreSQL 14+, sehingga konstruksi ini memerlukan verifikasi versi target. PostgreSQL juga memberi semantik khusus pada NaN. [PostgreSQL 14 Numeric Types](https://www.postgresql.org/docs/14/datatype-numeric.html)

**Rekomendasi default:** jangan mempertahankan ketergantungan literal numeric Infinity sebelum versi target diketahui. Pertimbangkan bounded `NUMERIC` atau floating type dengan finite/NaN guard yang diuji. Untuk confidence, `NUMERIC(6,5)` adalah kandidat; validasi nilai input sebelum pembulatan tetap diperlukan. Tidak ada SQL yang diubah.

## Syarat minimum keamanan sebelum tabel digunakan

1. Pilih auth dan sumber identitas request.
2. Lindungi dashboard dan setiap endpoint admin; backend memverifikasi ADMIN, bukan menerima role dari browser.
3. Tetapkan schema exposure dan grants. Desain RLS/policy least-privilege sebelum akses client, lalu uji anon/user/admin. Tabel di schema API yang terekspos tanpa RLS dapat diakses oleh role yang memiliki grant; default exposure/grants berbeda menurut konfigurasi/project. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase API Security](https://supabase.com/docs/guides/api/securing-your-api)
4. Publishable key hanya di client dalam pola yang dilindungi RLS. Secret/service-role hanya server-side; key elevated dapat melewati RLS sehingga backend melakukan pemeriksaan akses sendiri. [Supabase API Keys](https://supabase.com/docs/guides/getting-started/api-keys)
5. Bucket `waste-images` private; tetapkan policies, upload ownership, path, signed URL lifetime, dan retensi sebelum mengembalikan gambar.
6. Uji allow/deny database dan Storage di non-produksi sebelum production.

## Tahap berikutnya

Setelah keputusan dan versi PostgreSQL terkonfirmasi, revisi data dictionary dan SQL draft dalam perubahan ter-review; parse/eksekusi pada PostgreSQL lokal dengan versi sesuai; siapkan migration baru terpisah; review RLS/Storage bersama backend; lalu uji non-produksi. Jangan menerapkan ke remote tanpa review dan persetujuan eksplisit.
